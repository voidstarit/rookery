# AGENTS.md

Rookery is a self-hosted VM and network manager for Linux. The repository contains the Go
API with an embedded web UI, the `vnfs` DHCP/DNS/BGP daemon, QEMU/KVM lifecycle
management, LVM thin storage, and FD.io VPP networking.

## Go API
- `design/` is the protobuf source of truth for the API. It uses direct `protoc` via the root Makefile, not `buf`. Third-party protos are vendored under `design/third_party`; generated Go/gRPC/gateway/validation code and OpenAPI are committed under `design/gen` and `design/openapi`. Use `make proto-tools`, `make proto-generate`, `make proto-compile`, and `make proto-check`. Request validation uses `protoc-gen-validate`; the gateway under `internal/gateway` exposes all generated services for system, VMs, disks, media, networks, interfaces, ACLs, VNFs, storage backends, host interfaces, troubleshoot, and capture through an in-process gRPC server and grpc-gateway. VM/disk/media/network/interface/ACL/storage writes, VM lifecycle actions and metrics, interface ACL assignment, storage disk import, VNF status/lease/session views, troubleshoot/capture, and VNF writes are implemented. VNF writes and network deletion are implemented in `internal/lifecycle`, backed by the VPP/NAT/DHCP runtime exposed by `internal/api`; the old JSON handlers have been removed. The gateway emits 64-bit JSON fields as numbers and maps create/delete responses to `201`/`204`. Network deletion uses a native lifecycle method that stops VNFs, removes any BVI and bridge domain, then deletes the record. VM lifecycle and disk provisioning share the server's mutexes so gateway and native handlers cannot race. The main `serve` HTTP listener routes `/api` through the grpc-gateway and mounts `api.Server.NativeHandler` only for VNC WebSocket, pcap downloads, and static UI. `api.New` now builds only this native handler. `serve -gateway-addr` adds an optional second gateway HTTP listener and `serve -grpc-addr` exposes direct gRPC. Keep WebSocket VNC and streamed pcap downloads on native HTTP handlers because gateway does not proxy those protocols.
- `cmd/rookery` has two commands: `init` prepares host prerequisites (idempotently creates/verifies the thin pool and pings the VPP binary API), while `serve` runs the generated gateway API plus a Preact/TypeScript UI built from `ui/`. `internal/api` handles HTTP, `internal/store` owns SQLite and migrations, `internal/host` wraps LVM/GoVPP and runs CoreDHCP VNFs, `internal/qemu` launches QEMU/KVM and owns VNC Unix sockets, `internal/readiness` caches prerequisite status, and `internal/webui` embeds the UI. `cmd/rookery`, `cmd/vnfs`, and `internal/config` support a YAML file through `-config` / `ROOKERY_CONFIG`; one file may contain `api:` (serve/init) and `vnf:` (daemon) sections. Precedence is flags > environment > file > defaults, unknown fields are rejected, and `config.example.yaml` documents every key. `.github/workflows/release.yml` runs on `v*` tags, published releases, or manual dispatch with a tag and calls `make release VERSION=<tag>` to publish a static `linux/amd64` archive containing `rookery`, `vnfs`, `terraform-provider-rookery_<version>_linux_amd64`, `config.example.yaml`, `README.md`, `docs/`, and scripts, plus SHA-256 files. The Terraform provider is also published as a standalone release asset. `make release` builds the UI first and sets the provider version from `VERSION`.
- UI sources live under `ui/src`; `make ui-build` typechecks with `tsc` and bundles with esbuild into `internal/webui/static/build`, which is committed and embedded by `go:embed static`. Edit sources, not generated bundles. `make build` builds the UI and Go binary; `make ui-watch` rebuilds on change. SQL migrations (`internal/store/migrations`) also use `go:embed`; keep runtime assets inside those trees and avoid CDNs. noVNC v1.7.0 is vendored under `internal/webui/static/novnc` (MPL 2.0) and is imported as an external browser module by the console bundle; do not replace it with a CDN. The UI is fully Preact/TypeScript: the console page (`ui/src/console`) and inventory tabs (`ui/src/inventory/{vms,disks,media,networks,vnfs}`) are components, while `ui/src/inventory/app.ts` is the typed tab/readiness shell. The shell and tab islands communicate through `rookery:*` window CustomEvents (`vms-changed`, `add-vm`, `readiness-changed`, `networks-changed`, `interfaces-data`, `interfaces-changed`, `add-network`, `open-tab`, `disks-data`, `disks-changed`, `add-disk`, `media-data`, `media-changed`, `add-media`, `vnfs-data`, `vnfs-changed`, `vpp-ready`, `add-vnf`, `refresh-networks`, `tab-changed`); keep these bridges in sync. Inventory routing is path-based (`ui/src/inventory/router.ts`): tabs are `/vms`, `/disks`, `/media`, `/networks`, `/vnfs`; dialogs use deep links such as `/vms/new`, `/vms/{uuid}/edit`, `/interfaces/{id}/acls`, and `/vnfs/{id}/leases`. `internal/webui.Handler` must keep serving `index.html` for HTML navigations that do not match an embedded asset, or refreshing a deep link returns 404.
- Inventory UI HTTP calls go through `ui/src/shared/api.ts`. It shares in-flight GETs, retries transient failures after 1s/2s/4s/10s, then fails with an `APIError` naming the method and path. Mutations only retry `429`/`503` to avoid duplicate creates. Do not add unbounded retries or unguarded polling loops.
- VM IDs are UUIDs (`internal/store/migrations/0004_vm_uuid.sql`). Use UUID paths/validation consistently; disk and media IDs remain integers.
- `POST /api/vms` creates the VM and starts it immediately; stopping a VM is always an explicit `/stop`. When the QEMU start fails, creation rolls back the VM record (and stops any partial QEMU process) and returns the start error, so callers never see a half-created VM. `vms.desired_state` (`0038_vm_desired_state.sql`) records whether the VM should be running: start sets `running`, stop sets `stopped`, and creation sets `running` after a successful start. On API startup (and after a VPP restart) `internal/api.reconcileInfrastructure` calls `autostartVMs`, which starts every VM whose desired state is `running` and whose QEMU process is gone; explicitly stopped VMs stay down. Autostart runs after the VPP resources are reconciled so vhost-user sockets exist, holds the shared run mutex, and logs (without failing reconciliation) when a VM cannot start. `POST /api/vms/{id}/start` and `/stop` drive `internal/qemu`. QEMU runs with KVM (`-accel kvm`), every attached thin-LVM disk as a virtio drive (in `vm_disks.position` order), optional read-only CD-ROM boot media, and `-nic none`. VMs with attached vhost-user interfaces also get `-object memory-backend-memfd,...,share=on` plus `-numa node,memdev=mem`; without shared guest RAM VPP cannot map the virtqueues and the vhost link stays down. VNC is exposed only as a Unix socket under `-run-dir` (default `/run/rookery`). Vhost-user chardevs use `reconnect=1` so QEMU reconnects when VPP recreates its sockets after a restart. QEMU always exposes a `qemu-vdagent` virtio-serial channel (`com.redhat.spice.0`); guests with `spice-vdagent` can exchange clipboard text with the console, while guests without it ignore the port. A QEMU monitor socket (`<uuid>.monitor`) is local-only and used for `SendCtrlAltDel` (`sendkey ctrl-alt-delete`) and `Reset` (`system_reset`). `QEMU.Running` checks the pid file first and falls back to scanning `/proc` for `-uuid <vmID>`, so a QEMU process that survived an API restart or lost its pid file is still detected; start is then idempotent and repairs the stored status, while stop terminates the orphan by pid. QEMU start failures report the pid/name of a process holding one of the VM disks if the image lock is taken, and `reconcileVMStatuses` aligns DB status with live QEMU processes at startup.
- cgroup v2 resource management is in `internal/cgroup` and integrated through `internal/qemu`. Host settings and reusable class definitions (CPU cpuset, memory.max, cpu.weight, per-device io.max/io.weight, and slash-separated class paths such as `prod/web`) are stored in `cgroup_settings` (`0039_cgroup.sql`) and managed by `GET`/`PUT /api/cgroup-settings`. VMs store only `vms.cgroup_class` (`0040_cgroup_classes.sql`); an empty class selects the shared cgroup. `serve -cgroup-root` (default `/sys/fs/cgroup/rookery-cgroup`) creates a parent cgroup with no processes, a `shared` child, and class cgroups directly below the root (`<root>/prod/web`). Classes are limited to three levels below the `rookery-cgroup` root and must have their parent class defined; VMs may only be assigned to leaf classes, while parent classes group children and distribute controllers. Class nodes inherit host/parent limits; omitted class values inherit. Every QEMU start obtains a placement from `cgroup.Manager` and uses `SysProcAttr.UseCgroupFD` (plus a `cgroup.procs` fallback) so all QEMUs run under the hierarchy. `/api/host/block-devices` lists whole devices for the I/O picker; devices are resolved to major/minor with `DeviceNumber`. Settings are validated and rolled back on kernel apply failures, and removing a class assigned to a VM is rejected. VM updates apply class changes live through `QEMU.ApplyCgroup`, which moves the running QEMU process between the shared and leaf class cgroups without restarting it. Host settings saves also call `ApplyCgroup` for every running VM (via `systemService.applyCgroupsToRunningVMs`), so enabling limits or changing host defaults takes effect immediately; failures are reported per VM after the host settings are saved. Class limits require host-wide cgroup limits to be enabled. Disabling host settings moves every process out of the Rookery hierarchy and removes the cgroups, so no QEMU process remains constrained.
- `GET /api/vms/{id}/metrics` returns process-level QEMU metrics from `/proc` (summed per-thread `schedstat` CPU, `VmRSS`/`VmSize`, and `/proc/<pid>/io` counters). The endpoint also sums VPP vhost-interface RX/TX counters (via `vppctl show interface <name>`) for the VM's interfaces. The UI **Monitor** dialog polls it every 2s, derives CPU/disk/network rates, and keeps 60 samples for dependency-free canvas history charts; stopped VMs return `running:false`. Do not present these as guest-OS metrics.
- `POST /api/vms/{id}/ctrl-alt-del` and `/reset` inject those commands through the QEMU monitor. The console's Ctrl+Alt+Del button uses the API path first and falls back to VNC key events; Reset falls back to a stop/start power cycle when the monitor socket is missing (for VMs started by older servers).
- `GET /ws/vms/{id}/vnc` proxies the WebSocket to the VM's VNC Unix socket. Keep the `responseRecorder` in `internal/api/server.go` implementing `http.Hijacker` (and `Flush`), or WebSocket upgrades break. The UI console page is `/console.html?vm=<uuid>` and uses the vendored noVNC client. It includes a sticky-modifier virtual keyboard; key definitions use noVNC's `KeyTable` keysyms and standard `KeyboardEvent.code` scancodes. The console **Paste** dialog can type text as US keyboard events (the reliable fallback for guests without clipboard tools) or send it through noVNC `clipboardPasteFrom`, optionally reads the browser clipboard, and falls back to a manual text box when clipboard permissions are unavailable.
- `serve` must start even when prerequisites (or the VNF daemon) are missing. It reports state via `GET /api/status`, blocks default-backend disk creation when the bootstrap thin pool is not ready, and blocks `POST /api/vms` until the thin pool, VPP, and at least one unattached disk are ready. Additional storage backends are validated by their driver when a disk is created. Media registration has no readiness gate. Do not turn readiness into a startup failure; QEMU/KVM availability is checked when a VM is created or started.
- Storage backends are records in `storage_backends` (`0011_storage_backends.sql`): name, title, description, driver, JSON config, and disk count. Only driver `lvm-thin` is implemented now (`config.vg`, `config.thin_pool`, `config.supports_templates`, `config.preparation_script`, `config.preparation_timeout`, `config.allow_template_delete_with_clones`); keep the driver field and API shape extensible for future drivers such as Ceph. `serve` bootstraps a `default` backend from `-vg`/`-thin-pool` when supplied and associates legacy disks with matching `vg`/`thin_pool`; without those flags it uses the first registered backend and updates readiness when a backend is added in the UI. CRUD is at `/api/storage-backends`; changing the driver, volume group, or thin pool is blocked while disks use it, while template/script settings may be updated. Deleting a backend with disks is blocked. LVM backends expose `GET /api/storage-backends/{id}/importable-disks` and `POST /api/storage-backends/{id}/import-disks`; import registers existing thin volumes (via `lvs`) transactionally, marks already-registered volumes, does not mutate LVM, and sizes are rounded up from `lvs --units g`.
- Bridge-domain pipes (`network_pipes`, migration `0033_network_pipes.sql`) connect two Rookery Networks with a VPP pipe pair. `GET`/`POST /api/network-pipes` and `DELETE /api/network-pipes/{id}` manage them; a pair of networks can have only one pipe, and a network with a pipe cannot be deleted. `internal/host.CreatePipe`/`EnsurePipe` create or find the pipe by VPP instance, attach both ends to the selected bridge domains with a 1500-byte MTU, and roll back a newly created pipe on failure. The API recreates recorded pipes after a VPP restart and refreshes their runtime indices. The generic `/api/vpp/interfaces/{name}/addresses` endpoint recognizes the pipe endpoint names (`pipe<instance>.0`/`.1`), so users can assign IPv4/IPv6 addresses to either end; those addresses are persisted in `vpp_interface_addresses`, reapplied after restart, and cleaned up when the pipe record is deleted. The UI exposes them as the **BD pipes** subtab with per-endpoint address actions.
- Disks are first-class LVM-backed resources: `POST /api/disks` selects a `storage_backend_id` (or the default backend), runs `lvcreate` for a blank thin volume, or invokes the backend preparation script to clone a template when `template_disk_id` is supplied. Template and clone disks are recorded in migration `0013_disk_templates.sql`; templates are backend-scoped, cannot attach to VMs, and cloning requires `supports_templates` plus a configured script. The script runs as the API user, receives `ROOKERY_DISK_JSON` (operation, request id, disk, template, backend), has a configurable timeout, logs output, and must create the clone LV/device. Template disks may also configure `provisioning_script`/`provisioning_timeout` (`0037_disk_template_provisioning.sql`); after the preparation script creates the clone, Rookery runs it as the API user with `ROOKERY_PROVISION_JSON` (`operation`, request id, disk, template, backend, and arbitrary caller `properties` from the clone's `provisioning` JSON), and rolls back the clone on failure. `scripts/template-provision.sh` is the reference example; it logs each stage and always unmounts the clone. `PUT /api/disks/{id}` marks/unmarks templates; deleting a template with clones requires `allow_template_delete_with_clones`. `DELETE /api/disks/{id}` still removes empty and clone LVs, with script-based removal for script-created clones. VMs can have multiple disks through the `vm_disks` join table (`0012_vm_disks.sql`); `vms.disk_id` remains the legacy primary/first-disk column and is kept in sync. VM creation requires at least one `disk_ids` entry (`disk_id` is accepted as a single-disk alias); `PUT` with `disk_ids` replaces the set only while stopped, and omitting it preserves the set. A disk can attach to only one VM; deleting a VM releases all of its disks. Keep the host operations and store records consistent (rollback the LV if the DB insert fails; delete the LV before the record).
- Installation media are read-only path-backed records: `POST /api/media` stats an existing absolute regular file, records its server-derived size, and never copies or modifies it. `DELETE /api/media/{id}` removes only the inventory entry and is blocked while a VM uses the media as boot media.
- VMs have an optional `boot_media_id`. It may be set on create and changed or cleared on `PUT`; unlike disks, one media entry can be used by multiple VMs.
- Console access is controlled by `vms.console_enabled`. New VMs default to disabled; migration `0005_console_access.sql` enables existing VMs. The VNC WebSocket returns `403` when disabled and rechecks every second, closing live sessions after an administrator disables access. Keep this enforcement server-side; hiding the UI button alone is not sufficient.
- Rookery Networks are VPP bridge domains (`networks`) and vhost-user interfaces (`virtual_interfaces`). `POST /api/networks` and `POST /api/interfaces` provision VPP objects through `internal/host.VPPNetwork`; attach/detach is DB-only and must be blocked while the target VM is running. VM creation accepts optional `interface_ids`; VM update accepts `interface_ids` plus `replace_interface_ids` (omitted preserves attachments; an empty list with the replace flag detaches all) and must reject interface changes while QEMU is running. VM start turns each attached interface into a QEMU vhost-user netdev; VM deletion detaches its interfaces. VPP state is in memory; on API startup, bridge domains, vhost-user interfaces (by name), NAT44/BVI state, and VNF taps are reconciled. QEMU chardevs use `reconnect=1`, so VMs started with the current arguments can reattach after the vhost socket is recreated; VMs started by older servers without reconnect still need a restart.
- ACLs are named ordered permit/deny rule sets in `acls` (`0010_acls.sql`), with `virtual_interfaces.ingress_acl_id`/`egress_acl_id` kept as the first entry of each direction for compatibility and ordered assignments in `interface_acls` (`0016_interface_acls.sql`). Each rule also has its own optional description (documentation only). Rules support CIDR prefixes, protocols, and TCP/UDP port ranges; VPP enforcement uses the ACL plugin (`acl_add_replace`, `acl_interface_set_acl_list`) and `vpp_index` persistence. ACLs are assigned by name through `PUT /api/interfaces/{id}/acls`, which accepts repeated `ingress_acls`/`egress_acls` in evaluation order (the legacy single `ingress_acl`/`egress_acl` fields still work); the UI labels ingress as **From interface** and egress as **To interface**, with up/down ordering. Assignment requires VPP readiness. Reconcile ACL definitions and interface assignments after vhost reconciliation and on VPP restart. Deleting an assigned ACL is blocked. The UI lives under **Rookery Networks**, includes a rule editor with full ACL preview, and shows assignments on interface rows.
- Route tables are VPP IP FIB/VRF definitions in `route_tables` (`0017_route_tables.sql`); table `0` is the implicit default for both families and is synthesized in `RouteTableService`, not stored. Custom tables have a name, table ID, and IPv4/IPv6 family, with unique `(table_id, is_ipv6)` and `(name, is_ipv6)`. `PUT /api/interfaces/{id}/route-tables` binds `ipv4_table_id`/`ipv6_table_id`; `virtual_interfaces` stores both and defaults them to the owning network's `route_table_id` at creation (migration `0036_route_table_names.sql` backfills existing all-zero rows), while `interfaceSelect` joins the table names. Static entries live in `routes` (`0018_routes.sql`): table ID/family, prefix, next hop, and an optional egress — either an inventory interface (`interface_id`) or any VPP interface by name (`egress_interface`, added in `0019_route_egress_interface.sql` for BVIs/network gateways; resolved via `SwIfIndexByName` from the `sw_interface_dump` at install/reconcile time), plus a path `preference` metric — with a unique `(table_id, is_ipv6, prefix)`. The next hop is optional when an egress is set, which installs an attached/glean route (`ip route add <prefix> table N via <interface>`) instead of requiring ARP for a gateway; note that a "via <gateway> dev bviX" route where the gateway *is* the BVI's own address can never resolve, so interface-only routes are the way to import a bridge-domain subnet into a VRF. VPP's binary API has a dangerous sentinel: a recursive path (next hop resolved by table lookup) must send `sw_if_index = ^uint32(0)` and a valid path `table_id` (the resolve table); Go zero values mean "interface 0 / local0" and table 0, which produced silently unresolvable `via … local0` routes. `AddRoute` and `AddBGPRoute` set the sentinels. `GET`/`POST /api/route-tables/{id}/routes?ipv6=<bool>` list/add entries and `DELETE /api/routes/{id}` removes one; routes in the default table use ID `0`. The UI's route editor offers Rookery interfaces and network BVIs in the egress picker and a metric field. VPP uses `ip_table_add_del`, `sw_interface_set_table`, and `ip_route_add_del`; startup reconciliation ensures custom tables, reapplies interface bindings, then reinstalls routes. `GET /api/route-tables/{id}/fib?ipv6=<bool>` reads the live VPP FIB with `ip_route_v2_dump`, including connected, DHCP, ND, and adjacency entries with source names and paths; the route editor shows these read-only as **Dynamic routes** for troubleshooting. Next hops resolve only within the route's own table — a route in a non-default VRF needs that table to contain a route to the next hop (bind the owning interface into the table, or add an egress-interface route). Deleting a custom table is blocked while an interface or route references it. The UI has a **Route tables** subtab, an interface-level binding dialog, and a per-table route editor. Next-hop and IPv4/IPv6 lookup options store route-table names in `next_hop_table_name`/`ipv4_lookup_table_name`/`ipv6_lookup_table_name` (resolved to current VPP table IDs at install/reconcile time; `default` means table 0) instead of numeric IDs; MPLS lookup remains numeric. Numeric route options preserve explicit presence: blank omits the CLI option, while `0` is persisted and emitted where supported. Host interfaces and host taps can also be bound with `GET`/`PUT /api/vpp/interfaces/{name}/route-tables`; those bindings live in `vpp_interface_route_tables` (`0034_vpp_interface_route_tables.sql`) and are reapplied after VPP/API restarts. Vhost-user interfaces keep using `virtual_interfaces.ipv4_table_id`/`ipv6_table_id`; the generic endpoints reject them. Route-table interface counts include both sources, so a custom table cannot be deleted while a host interface or tap uses it. A non-default binding overrides the interface's network VRF.
- The API server and the DHCP/DNS/BGP runtimes are separate processes. `cmd/vnfs` owns `host.VNFManager` (CoreDHCP, the DNS server, the gVisor memif stacks, and GoBGP) and exposes the internal `VNFDaemon` gRPC service (`design/proto/rookery/v1/vnfd.proto`, no HTTP annotations): `EnsureVNF` (idempotent start; restarts only when the spec hash changes), `RemoveVNF`, `ResetRuntime`, `ListVNFStates`, `ListLeases`, `ListDNSRecords`, `GetBGPStatus`, and `CleanupLegacyNetwork`. `rookery` connects through `internal/vnfd.Client` (implements `api.VNFManager` and `gateway.VNFRuntime`) using `-vnf-addr` / `ROOKERY_VNF_ADDR` (default `unix:///run/rookery/vnfs.sock`; `tcp://host:port` also works). The API still owns the database and every VPP operation (memif/tap creation, BVIs, NAT44); the daemon opens the VPP binary API socket itself only to install/withdraw BGP-learned routes, so a BGP session keeps updating the FIB while the API restarts. The daemon persists desired specs under `<run-dir>/vnfs/desired-<id>.json`, restores them on its own restart, and supervises runtimes (restarting dead ones after a 10s backoff; `ResetRuntime` pauses supervision for 60s so the API can rebuild VPP resources first). VNF runtime state is queried on demand (VNF views and reconciliation decisions), not by a background poll; reconciliation runs at API startup and after a VPP restart, and the daemon restores its persisted specs after its own restart. `serve` starts without the daemon; VNFs report `degraded` until it is reachable. On API startup, `ReconcileVNFs` re-sends current specs once to already-running VNFs; the daemon's spec hash makes this a no-op unless a desired spec is stale (for example after a daemon upgrade). `vnfs` flags: `-vpp-socket`, `-listen`, `-run-dir`, `-vhost-dir` (env `ROOKERY_VPP_SOCKET`, `ROOKERY_VNF_LISTEN`, `ROOKERY_RUN_DIR`, `ROOKERY_VHOST_DIR`).
- Network functions are first-class records in `vnfs` (`0008_vnfs.sql`): `dhcpv4`, `dhcpv6`, `nat44`, `bgp`, and `dns` types, a network, an enable flag, typed JSON config, and tap metadata. A network can have at most one VNF of each type; use separate networks for separate DHCP pools. The UI exposes a **VNFs** tab; `POST /api/vnfs`, `PUT /api/vnfs/{id}`, `DELETE /api/vnfs/{id}`, `POST /api/vnfs/{id}/restart`, `GET /api/vnfs/{id}/leases`, `GET /api/vnfs/{id}/sessions`, and `GET /api/vnfs/{id}/dns-records` manage and inspect them. BGP VNFs use the address family of `config.local_ip` (IPv4 or IPv6 unicast; peer, gateway, and advertised prefixes must match). `config.transport` selects `memif` (gVisor netstack over VPP memif) or `tap` (VPP tap plus kernel TCP). Both embed GoBGP in-process; memif uses a loopback TCP relay because GoBGP requires kernel TCP. The global RIB enables both families (`Families: []uint32{0, 1}` — GoBGP's AfiSafi index list), the peer negotiates the session family, and IPv6 advertisements use `PathAttributeMpReachNLRI`. BGP peer fields are local/peer AS, router ID, peer/local addresses, optional peer gateway, `config.next_hop` (overrides the NEXT_HOP announced with advertised prefixes; defaults to `local_ip`; same address family), multihop TTL (defaults to 64 when unset so replies survive routed topologies like a peer behind a BVI; TTL=1 only when explicitly configured), passive mode, optional TCP MD5 password (tap only; memif rejects it), raw target VPP table ID, and advertised prefixes. Imported best paths are installed in the target VPP table (IPv4 or IPv6) with `ip_route_add_del_v2` using the CLI FIB source and withdrawn when the session closes or the VNF stops; next hops come from `PathAttributeNextHop` (IPv4) or `PathAttributeMpReachNLRI` (IPv6). `GET /api/vnfs/{id}/bgp` returns a live snapshot from the embedded GoBGP server (via `bgpInstance.Status`): running/established flags, session state, peer address/AS, locally advertised prefixes, and received prefixes with next hop and AS path; note GoBGP reports `NeighborIp` as the literal string `"<nil>"` for locally originated paths, and its `ListPeer`/`ListPath` APIs are callback-style. The UI exposes it as a **Status** dialog on BGP rows (`/vnfs/{id}/bgp`). GoBGP is wired to VPP through `host.BGPRouteWriter`, set by `cmd/vnfs` with `vnfManager.SetBGPRouteWriter(networkRunner)`. The memif gVisor side must use `vnfMemifBGPMAC` (`02:4f:4d:…`), never `VNFMemifMAC` (`02:4d:4d:…`), because that MAC belongs to the VPP memif master port; both ends claiming the same MAC breaks bridge-domain learning and the peer cannot connect to `local_ip:179` (passive mode listens on 179 via gVisor, active mode dials `peer_ip:179`). The gVisor stack answers ICMP echo for `local_ip` automatically; when `peer_gateway` is set it also becomes the stack's default-route gateway so ICMP replies to routed (non-peer) sources survive the BVI hop, and same-subnet replies stay on-link via the connected route. The BGP runtime logs its memif socket/interface id/MAC, listen/dial addresses, the `127.0.0.1` relay ports, and every GoBGP session state transition (`BGP session state changed`); the shared memif slave also logs connect/disconnect events.
- Every network requires an IPv4 and an IPv6 CIDR (UI defaults `10.0.0.0/16` and `fd00:20::/64`; the API rejects missing/invalid CIDRs). `PUT /api/networks/{id}` updates both CIDRs and is blocked while the network has VNFs, host taps, legacy DHCP configuration, or a BVI/gateway; the UI exposes this as **Edit CIDRs**. Networks may reuse the same CIDRs because each has its own VPP VRF table (`networks.route_table_id = 100000 + network ID`, IPv4 and IPv6); table IDs in that range are reserved for networks and cannot be created manually. `ensureNetworkRouteTable` upserts `route_tables` records (`network-<name>`, `network_id` set, `managed`) for both families so they appear in the **Route tables** UI and accept static routes; `DeleteRouteTablesByNetwork` removes them with the network. The BVI, shared network memif, per-VNF tap/memif, and vhost-user interfaces are bound to the network table with `sw_interface_set_table`, so overlapping BVI addresses are isolated. `reconcileVNFBindings` also moves already-running VNF interfaces into the network VRF after an upgrade. The first five host addresses of each prefix are reserved for Rookery: `.1` is the network BVI, `.2` is the shared VNF memif stack, and `.3`-`.5` are reserved. DHCP ranges, static assignments, and DNAT local addresses must stay inside the network prefix and outside those reserved addresses; NAT44's gateway must be the network BVI (`prefix + 1`). The IPv6 CIDR defines the allowed IPv6 range and reservations; IPv6 BVI/memif address assignment will follow with shared DHCPv6.
- Shared VNF networking is the default for new and restarted DHCPv4 VNFs. `networks.vnf_transport` defaults to `shared`; a VNF's `config.transport` overrides it with `shared`, `dedicated`, or `tap`. Network creation creates one VPP memif master per shared network (`net<id>-vnf`, socket `<memif-dir>/net-<id>.sock`, high-bit socket ID) and stores it in `networks.vnf_memif_*`; reconciliation recreates it after a VPP restart. The first shared DHCPv4 activation creates the network BVI (`bvi<id>`) owning the gateway `.1` and sets the VNF bind address to the next host address `.2`; all DHCPv4 servers on the network share one gVisor stack on that memif. The daemon must receive `host.NetworkVNFMemifID(networkID)` (the high-bit memif interface ID) for the shared memif handshake, not the network's VPP `sw_if_index`; an ID mismatch makes VPP drop the slave after an initial connect. DHCPv6 remains tap-only, and BGP keeps its dedicated memif/tap transports for now. Running VNFs keep their old transport until restarted; after a VPP restart or VNF restart they migrate to the shared default (the old per-VNF memif is deleted).
- `internal/host.VNFManager` (inside `cmd/vnfs`) runs one in-process CoreDHCP server per enabled DHCP VNF. Each DHCP VNF gets a `vnf<id>` VPP tap, a gateway address, an allocator, and a JSON lease file under `<run-dir>/vnfs/<id>.json`. DHCPv4 uses the bitmap allocator; DHCPv6 is stateful IA_NA (no RA/PD). DHCPv4 also supports `static_assignments` (unique MAC/IPv4 pairs): reserved addresses are excluded from the dynamic pool, may sit inside or outside the DHCP range, and must not be the gateway or service address. Static assignments are DHCPv4-only. Leases are surfaced by VNF ID, and status is `running`, `disabled`, or `degraded`. Enabling/restarting needs VPP, UDP 67/547, `SO_BINDTODEVICE`, and tap configuration, so it needs root or `CAP_NET_ADMIN` + `CAP_NET_BIND_SERVICE` + `CAP_NET_RAW`. Failures must roll back the tap and leave the VNF disabled.
- DHCP VNFs additionally accept `config.dhcp_options` (`code`, `format`, `value`, max 64) for extra DHCPv4/DHCPv6 options. `format` is `string`, `ipv4`, `ipv6`, `hex`, `uint8`, `uint16`, `uint32`, or `domain-list` (DNS wire-format domain names). `host.NormalizeDHCPOptions` canonicalizes values and rejects server-managed codes (v4: 1, 28, 51, 53, 54, 58, 59; v6: 1, 2, 3, 5, 6, 7, 8, 9, 13, 14, 25, 26) and duplicate codes. The values are JSON-encoded into the CoreDHCP plugin arguments; DHCPv4 applies them as generic options on every reply, while DHCPv6 only sends options the client requested in its ORO. Custom router/DNS options (v4 3/6, v6 23) override the gateway/DNS fields because they are applied after the defaults. Use code 15 for a domain name, 42 for NTP, 119/24 for the domain search list. The UI suggests common codes, labels them, and auto-selects the matching format.
- DNS VNFs (`0008_vnfs.sql` config JSON; no schema change) run on the network's shared gVisor stack too. `StartShared` dispatches DHCPv4 and DNS to one stack per network; the DNS listener binds UDP/TCP 53 on the service address `.2` over IPv4 and IPv6 and does not create a tap or dedicated memif. The shared stack receives both IPv4 and IPv6 service addresses from the API. `config.dns_records` (name, type A/AAAA/CNAME/TXT/PTR, value, TTL; wildcard names such as `*.lab1.test` are supported) is authoritative; `config.dns_forward` controls whether unknown names are sent to `config.dns_forwarders` (IP or IP:port, default port 53). With forwarding enabled and no forwarders, the daemon reads `/etc/resolv.conf`; with forwarding disabled, unknown names get NXDOMAIN. Local records override forwarding. `activateSharedDNS` forces the shared memif even when the network default transport is tap/dedicated, so DNS requires the VNF daemon but no per-VNF tap. DHCPv4/DHCPv6 VNFs can select a DNS VNF on the same network with `config.dns_vnf_id`, `config.dns_domain`, and `config.dns_ttl`; the daemon reconciles active lease files into dynamic A/AAAA and PTR records every second, preferring DHCP FQDN, then hostname plus suffix, then a MAC/DUID-derived name. Records are removed on release/expiry; deleting a DNS VNF is blocked while referenced. The UI uses the **DNS** type in the VNF form, with a record editor and forwarding controls; clients should use `.2` as their DNS server (set it in the DHCP VNF's `config.dns`). DNS rows expose a **Records** dialog (`/vnfs/{id}/dns`) that lists configured static records and live lease-derived records together; the endpoint merges store records with `VNFDaemon.ListDNSRecords` output and still shows static records when the daemon is unavailable.

- DHCPv4 uses a memif transport by default. With the network default `shared` (or `config.transport=shared`), one gVisor stack per network (`internal/host/memif_shared.go`) connects to the network memif, owns the `.2/prefix` VNF address, and serves every DHCPv4 VNF on that network; the network BVI owns `.1`. With `config.transport=dedicated`, the legacy per-VNF memif path (`internal/host/memif_dhcp.go`, socket `<memif-dir>/<vnf-id>.sock`, interface name = VNF name) is used; on non-NAT networks that stack owns the gateway address directly. `tap` falls back to a per-VNF tap. VPP is always the memif master; the VNF daemon is the slave using `go.fd.io/govpp/extras/gomemif/memif` (do not vendor or replace it). The shared stack binds UDP/67 on the DHCP `BindIP` (`.2`) and reuses the CoreDHCP plugin handler. `-dhcp-transport memif` / `ROOKERY_DHCP_TRANSPORT=memif` enables memif at all; `tap` disables it. DHCPv6 still uses the tap path. The memif socket directory is `-memif-dir` / `ROOKERY_MEMIF_DIR`.
- Host NIC takeovers are persisted in `host_interfaces` (`0023_host_interfaces.sql`, `internal/store/host_interfaces.go`). `POST /api/host/interfaces/{name}/attach` and `DELETE /api/host/interfaces/{name}` manage them through `HostService`; the gateway validates that the NIC is a physical, non-wireless interface without the host default route, calls `host.VPPNetwork.EnsureHostInterface`, and stores `nic`, `host-<nic>`, sw_if_index, and purpose (`manual` or `nat44`). NAT44 activation records its outside NIC automatically. `ReconcileHostInterfaces` recreates every persisted `host-<nic>` after a VPP restart and refreshes its sw_if_index; a stale/missing NIC is logged and retried. AF_PACKET host interfaces are created with `rx-size 69632` and `rx-per-block 1` so GRO/GSO packets up to 64 KiB fit in one RX frame (VPP's 2048-byte default silently drops them as partial packets, which throttles downloads while uploads stay fast). They are tagged `rookery-afpacket-rx69632-v1`; reconciliation recreates an older untagged host interface once, and NAT44 is reapplied afterwards. The Linux NIC is also set to `gro off`/`lro off` (RX) while `tso on`/`gso on` (TX) are kept enabled, because NAT44 rewriting coalesced RX GSO packets causes heavy TCP retransmissions; this needs the `ethtool` binary. Rookery also pins BVI, vhost-user, memif, and tap MTUs to 1500 instead of VPP's 9000 default. Detach refuses an interface referenced by a NAT44 VNF and does not restore host IPs (renew DHCP on the NIC). The UI's **Host interfaces** section has Attach/Detach actions for eligible NICs.
- Network host taps are persisted in `network_host_taps` (`0026_network_host_taps.sql`, `internal/store/network_host_taps.go`) and exposed as `GET`/`POST /api/host/taps` and `DELETE /api/host/taps/{id}`. `POST` takes `network_id`, optional `name` (Linux limit 15, defaults to `hostnet<id>`), and optional `ipv4_address` (CIDR matching the network prefix, outside the reserved `.1`-`.5` addresses, DHCP range, and static assignments). `host.VPPNetwork.EnsureHostTap` creates a tagged VPP tap (`rookery-host-tap:<name>`) in the network bridge domain, configures the Linux tap (`ip addr replace`, link up), and is idempotent. `internal/api.Server.CreateNetworkHostTap` writes the record first, binds the interface to the network VRF, and rolls back both VPP and the record on failure; lifecycle deletion removes host taps before the bridge domain. `ReconcileNetworkHostTaps` runs after bridge domains in startup/VPP-restart reconciliation, recreates missing taps, and refreshes `sw_if_index`. Deleting a network removes its host taps. The UI's **Host taps** subtab creates and deletes them.
- NAT44 is IPv4-only (`internal/host/nat44.go`, `internal/api/nat44.go`). It creates a per-network BVI (`bvi<id>`) and stores `bvi_host_name`, `bvi_sw_if_index`, and `ipv4_gateway` on `networks` (`0009_nat44.sql`). Enabling it refuses any host default-route NIC and wireless NICs, flushes the selected wired outside NIC, creates a VPP `host-<nic>` using the physical NIC's MAC (random MACs break upstream ARP/switch port security), configures NAT44-ED via the binary API (interface features are not idempotent in the VPP CLI), and uses a static outside address/default route or the VPP DHCP client (which installs its leased address and default route). DNAT/port-forwarding rules live in `VNFConfig.DNATRules` and are applied as VPP NAT44 static mappings through `Nat44AddDelStaticMappingV2`; use the outside interface's `sw_if_index` so the external address follows DHCP changes, and tag mappings `rookery:<vnf-id>:<rule-index>` so applying/removing one VNF never touches another VNF's rules. Apply DNAT mappings after `ApplyNAT44` and remove them before `RemoveNAT44`. Startup reconciliation order is bridge domains, enabled NAT44 VNFs, then DHCP VNFs. A DHCPv4 VNF on a NAT network runs on `.2` while the BVI owns `.1`; `BindIP` is the server ID and must not be compared with `gateway` in DHCP request filtering. Validate/take over the outside interface before creating a BVI, roll back a newly created BVI when activation fails, and remove a leftover BVI when deleting a NAT44 VNF unless another NAT44 or NAT-adjusted DHCPv4 VNF depends on it.
- On API startup, `internal/api.Server.RunInfrastructureReconciler` waits for VPP, ensures every recorded network bridge domain exists with its stored ID (`EnsureBridgeDomain`), finds or recreates every recorded vhost-user interface by name and updates its `sw_if_index`/socket metadata, restores ACL definitions/assignments, restores enabled NAT44 VNFs, then restarts every enabled DHCP VNF, reusing an existing `vnf<id>` tap and recreating a missing/migrated tap. A VPP restart removes vhost-user interfaces, ACL state, NAT44 state, and VNF taps; API startup restores them; QEMU reconnect lets current VMs reattach, while older QEMU processes may need a restart. While running, `RunInfrastructureReconciler` control-pings the VPP API every five seconds and compares the API socket identity; on restart it resets cached NAT/VNF runtime state and repeats the reconcile sequence automatically. Reconciliation runs in a bounded background worker (2 minutes) so API pings/identity checks continue; a further VPP restart queues another rebuild after the in-flight worker finishes (workers must not overlap, because concurrent BVI creation aborts VPP). `vppctl` calls have a 10-second timeout so a disappearing CLI socket cannot wedge the reconciler.
- Migration `0008_vnfs.sql` converts existing network-level DHCP settings into a DHCPv4 VNF. On the first startup reconciliation or manual restart, `internal/api.cleanupLegacyNetworkVNF` removes the old `ndn<network-id>` tap and legacy DHCP files. The old network DHCP API/UI is removed; do not add new code that writes the legacy `networks.dhcp_*` columns.
- `internal/api.Server.resourceMu` serializes disk provisioning with VM attachment; preserve it or replace it with equivalent concurrency control.
- The Network tab includes a **Troubleshoot** section. `GET /api/troubleshoot/vpp-graph` runs `vppctl show vlib graphviz filter`, parses the active nodes and edges, and returns them as JSON; the UI renders a dependency-free layered top-to-bottom SVG with input nodes at the top, terminal/drop nodes at the bottom, barycenter ordering to reduce crossings, and dashed feedback edges. Interface-related nodes are ringed and a **Focus** picker filters the graph to one interface group or packet feature (ACL plugin, NAT44, DHCP) plus its direct neighbors; hover isolates a node and its direct neighbors, and labels/edges for everything else are hidden. It supports wheel/button zoom, drag-to-pan, Fit, and a Labels toggle. VPP's CLI pager can split long DOT node lines across physical lines, so join quoted statements until complete instead of parsing one statement per line. Node size represents cycles/packet and color represents packets/call. Interface nodes only exist in the graph when active since the last stats clear. Packet capture lives in the separate capture endpoints described below. The same Troubleshoot UI has packet trace controls: `POST /api/troubleshoot/trace` clears the trace and runs `vppctl trace add <node> <count>` (count 1–1000), `GET /api/troubleshoot/trace` returns `vppctl show trace` output, and `DELETE /api/troubleshoot/trace` clears it. The node picker is populated from `GET /api/troubleshoot/trace/nodes`, which runs `show vlib graphviz` and returns every registered VPP node (not only active nodes); it also accepts typed names. Use `runCLIRaw` for `show trace` because packet text may contain words like "invalid" that the generic CLI failure heuristic would misclassify. Keep the `vppctl` timeout and VPP readiness checks when extending these endpoints.
- The VPP socket is the binary API socket (`socksvr`, default `/run/vpp/api.sock`), checked with `go.fd.io/govpp`, not the CLI socket or a vhost-user socket. NAT44 also shells out to `vppctl` (default CLI socket) for plugin/address/session commands, so it must be on `PATH` with CLI socket access. `GET /api/host/interfaces` exposes physical and external host interfaces, link/address state, and whether each has a matching `host-<nic>` interface in VPP; Rookery/VPP-created interfaces (`vnf*`, `tap*`, `host-*`, etc.) are filtered out. Default-route takeover is blocked server-side.
- `GET /api/troubleshoot/acl-counters` exposes per-interface ACL rule-match counters by combining `show acl-plugin lookup context` with `show acl-plugin tables applied`. The `hitcount` values are explicit per-rule matches per lookup context (ingress/egress), split by action into denied/permitted and returned with ACL/rule indexes; implicit-deny packets are not counted. The UI shows compact totals and expandable per-rule counters in the Interfaces tab, where ACLs are assigned. Keep `VPPInterfaces` for the sw_if_index-to-name mapping.
- `GET /api/interfaces/counters` returns cumulative VPP RX/TX packet and byte counters for the registered vhost-user interfaces (via the same `vppctl show interface <name>` path as VM metrics); interfaces VPP has not recreated yet are omitted. The Interfaces tab polls it every 2s while visible and VPP-ready and derives per-interface RX/TX rates (speed) from consecutive samples. The tab shell keeps every tab component mounted and toggles panels with `hidden`, so the poll must gate on the current route being inside the Network tab (not just section state) or it keeps firing on other tabs. `DELETE /api/interfaces/counters` clears the counters for all VPP interfaces (`vppctl clear interfaces`); the UI resets its rate baseline after it succeeds. Both RPCs must stay declared after `GetInterface`/`DeleteInterface` in `interface.proto`: grpc-gateway registers handlers in declaration order and tries the newest first, so the literal `/api/interfaces/counters` path must beat the `/api/interfaces/{id}` pattern.
- Packet capture is managed by `internal/host/pcap.go` through `vppctl pcap trace`. VPP writes only a basename under `/tmp`, so capture files are named `rookery-<timestamp>-<random>.pcap` and read from `/tmp`. The API keeps one active capture; `max <packets>` is derived from the requested max size and snapshot length (`ceil(max_bytes/(snap_length+16))`, capped at 1,000,000). Capture listing/download/delete is available even when VPP is down; the active file cannot be deleted until capture stops. Endpoints live under `/api/troubleshoot/capture`; `VPPInterfaces` uses govpp for the picker. Like NAT44, capture requires the VPP CLI socket and root/CLI access.
- `TapCreateV2` must use `ID: ^uint32(0)` for automatic tap device allocation. Sending the Go zero value requests device instance 0; after the first tap exists, later taps fail with `VppApiError: Invalid interface (-71)`.
- SQLite uses the pure-Go `modernc.org/sqlite` driver, so builds need no CGO. The module targets Go 1.26 and pins `modernc.org/sqlite` v1.60.1.
- Public mTLS API: `serve -mtls-addr` (default `:8443`, `ROOKERY_MTLS_ADDR`; empty disables) starts a second HTTPS listener using `internal/pki`. It serves only the grpc-gateway handler and requires a client certificate signed by the server CA (`tls.RequireAndVerifyClientCert`, TLS 1.3, session tickets disabled). The CA/server certificate live under `-pki-dir` (`ROOKERY_PKI_DIR`, default `/var/lib/rookery/pki`); the server certificate SANs include localhost, hostname, host IPs, and `-mtls-sans`/`ROOKERY_MTLS_SANS`. Client certificates are issued by the native-only endpoints `GET /api/pki/ca`, `GET/POST /api/pki/clients`, and `DELETE /api/pki/clients/{id}`; these are routed to the native handler by `CutoverHandler` and are **not** exposed on the public mTLS listener (which serves the gateway handler directly). Issued private keys are returned once and not stored; metadata and revocation live in `client_certificates` (`0025_client_certificates.sql`), and `VerifyPeerCertificate` rejects revoked serials. The UI sidebar **Client certificates** item issues, downloads, lists, and revokes them.
- The local HTTP API has no authentication or authorization and binds to `127.0.0.1:8080` by default; do not expose it without an access-controlled proxy. The public mTLS listener is the authenticated API entry point.
- `serve` applies a per-path token-bucket rate limit to every request on both HTTP listeners (`-rate-limit` / `ROOKERY_RATE_LIMIT`, default 3 RPS per URL path, `0` disables); excess requests get `429` with `Retry-After: 1`.
- `gateway.New` supports extra gRPC listeners via `gateway.WithExtraGRPCListener`; `serve -grpc-mtls-addr` (default `:9443`, `ROOKERY_GRPC_MTLS_ADDR`) wraps a listener with `pki.Manager.TLSConfig()` and serves the same generated services alongside the optional plaintext `-grpc-addr` listener. The PKI TLS config must advertise ALPN `h2`; without it, grpc-go clients fail with `missing selected ALPN property`.
- `cmd/terraform-provider-rookery/` is a command in the main Go module (framework v1.18) implementing `rookery_*` resources and matching data sources over the mTLS gRPC endpoint: storage backends, disks, media, networks, network pipes, interfaces, host interfaces, host taps, VPP interface addresses and route-table bindings, ACLs, route tables, routes, VNFs, VMs, host cgroup settings with reusable classes (`rookery_cgroup_settings`), startup scripts, plus a `rookery_status` data source. VM resources and data sources expose `cgroup_class` for assigning a class; host cgroup classes carry CPU, memory, weight, and per-device I/O limits. Provider config accepts CA/client/key file paths or inline PEM and `server_name`; the client uses TLS 1.3, verifies the CA, and always presents the client certificate. The provider intentionally does not manage VM power actions. `rookery_route` exposes all VPP route path options (`route_count`, next-hop/lookup tables, weights, UDP encapsulation, resolve/rx flags, labels, drop, and description); optional numeric fields are nullable so an omitted value stays unset while an explicit `0` is sent to the API. `rookery_disk` exposes template `provisioning_script`/`provisioning_timeout` and clone `provisioning_json`. Build with `go build ./cmd/terraform-provider-rookery`; `examples/complete` and `examples/data-sources` are validated with Terraform `dev_overrides`.
- Verify with `go test ./...`, `go vet ./...`, and `gofmt -l .`; run locally with `go run ./cmd/rookery serve -db /tmp/rookery.db`.

## Conventions and gotchas
- Both binaries log through `zerolog` via `internal/logging.Setup`. `-log-level`
  (`ROOKERY_LOG_LEVEL`, default `info`) and `-log-format`
  (`ROOKERY_LOG_FORMAT`, `console` or `json`) configure the global logger, and
  every line is tagged `service=rookery` or `service=vnfs`. Components hold a
  `zerolog.Logger` value (tests use `zerolog.Nop()`); package-level events in
  `internal/host` and `internal/api` use `github.com/rs/zerolog/log`. Use typed
  builders (`.Str`, `.Int64`, `.Uint32`, `.Bool`, `.Dur`, `.Err`) rather than
  pre-formatting values into strings. At trace level, `internal/vnfd` logs every
  daemon RPC (via `TraceInterceptor`), client availability changes, supervision
  decisions, DHCPv4/v6 request/reply details, DNS queries/records/forwarding
  results, and BGP route installs/withdrawals. Lease allocation and release log
  at info; renewals at debug.
- `README.md` is the high-level project/install/run entry point. Detailed host, networking, API, operations, and development material lives under `docs/` with `docs/README.md` as the index; C4/Mermaid architecture diagrams are in `docs/architecture.md`. Keep details out of the main README and update the relevant docs page and index when behavior changes.
