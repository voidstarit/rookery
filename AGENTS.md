# AGENTS.md

Standalone Ansible playbooks (no roles, no `ansible.cfg`) that manage thin-LVM VM disks and FD.io VPP networking on a Debian host, plus a Go VM inventory API with an embedded web UI. Run each `*.yml` directly with `ansible-playbook`; `templates/` contains only the VPP startup config.

## Running safely
- Playbooks use `become: true` and mutate real remote LVM/network state. `hosts.ini` targets `baltic.void-star.co`; pass `-K` for the sudo password and prefer `--limit` or a test inventory over hitting the default host accidentally.
- Requires Ansible plus `community.general` (`ansible-galaxy collection install community.general`).
- No Ansible lint or test suite. Verify playbook edits with `ansible-playbook --syntax-check -i hosts.ini <playbook>` (all six currently pass). Check mode is unreliable because most work is done via `command`/`shell`.

## Playbooks
- `setup-thin-pool.yml` — creates the thin pool (default `nerds-vms`) inside an existing VG.
- `setup-template.yml` — downloads the Debian 13 cloud image and `dd`s it into a template LV. Auto-extends the thin pool if needed, but fails when pool metadata is >90% full or the VG lacks free space.
- `create-instance-disk.yml` — creates a thin snapshot of the base LV. LVM ignores `-L` when snapshotting a thin origin, so `disk_size` is applied with a separate `lvextend`; it must be >= the base LV size and accepts IEC units via `numfmt`.
- `configure-instance-user.yml` — offline image edit. Do not simplify its shell block: it uses `losetup --partscan` (the `partx` ioctl fails on device-mapper), handles GPT and LVM-in-image layouts, and imports clashing embedded VGs as `<disk_lv>-rootvg` with `vgimportclone`. Cleanup (unmount, `vgchange -an`, loop detach) lives in `always`.
- `delete-instance-disk.yml` — `lvol state=absent force=true`; immediate and destructive.
- `setup-vpp.yml` — installs/configures VPP. FD.io only publishes `bookworm` packages, and `trusted=yes` is intentional on trixie (apt's sqv rejects the SHA1 repo key). `vpp_host_tap` only creates the tap and prints manual NAT commands. `vpp_nat44` consumes a dedicated NIC via AF_PACKET: flush its IPs first and never point it at the management link.

## Go API
- `design/` is the protobuf source of truth for the API. It uses direct `protoc` via the root Makefile, not `buf`. Third-party protos are vendored under `design/third_party`; generated Go/gRPC/gateway/validation code and OpenAPI are committed under `design/gen` and `design/openapi`. Use `make proto-tools`, `make proto-generate`, `make proto-compile`, and `make proto-check`. Request validation uses `protoc-gen-validate`; the gateway under `internal/gateway` exposes all generated services for system, VMs, disks, media, networks, interfaces, ACLs, VNFs, storage backends, host interfaces, troubleshoot, and capture through an in-process gRPC server and grpc-gateway. VM/disk/media/network/interface/ACL/storage writes, VM lifecycle actions and metrics, interface ACL assignment, storage disk import, VNF status/lease/session views, troubleshoot/capture, and VNF writes are implemented. VNF writes and network deletion are implemented in `internal/lifecycle`, backed by the VPP/NAT/DHCP runtime exposed by `internal/api`; the old JSON handlers have been removed. The gateway emits 64-bit JSON fields as numbers and maps create/delete responses to `201`/`204`. Network deletion uses a native lifecycle method that stops VNFs, removes any BVI and bridge domain, then deletes the record. VM lifecycle and disk provisioning share the server's mutexes so gateway and native handlers cannot race. The main `serve` HTTP listener routes `/api` through the grpc-gateway and mounts `api.Server.NativeHandler` only for VNC WebSocket, WebShark, pcap downloads, and static UI. `api.New` now builds only this native handler. `serve -gateway-addr` adds an optional second gateway HTTP listener and `serve -grpc-addr` exposes direct gRPC. Keep WebSocket VNC, WebShark SSE/static assets, and streamed pcap downloads on native HTTP handlers because gateway does not proxy those protocols.
- `cmd/nerds-vms-api` has two commands: `init` prepares host prerequisites (idempotently creates/verifies the thin pool and pings the VPP binary API), while `serve` runs the generated gateway API plus a Preact/TypeScript UI built from `ui/`. `internal/api` handles HTTP, `internal/store` owns SQLite and migrations, `internal/host` wraps LVM/GoVPP and runs CoreDHCP VNFs, `internal/qemu` launches QEMU/KVM and owns VNC Unix sockets, `internal/readiness` caches prerequisite status, and `internal/webui` embeds the UI.
- UI sources live under `ui/src`; `make ui-build` typechecks with `tsc` and bundles with esbuild into `internal/webui/static/build`, which is committed and embedded by `go:embed static`. Edit sources, not generated bundles. `make build` builds the UI and Go binary; `make ui-watch` rebuilds on change. SQL migrations (`internal/store/migrations`) also use `go:embed`; keep runtime assets inside those trees and avoid CDNs. noVNC v1.7.0 is vendored under `internal/webui/static/novnc` (MPL 2.0) and is imported as an external browser module by the console bundle; do not replace it with a CDN. The UI is fully Preact/TypeScript: the console page (`ui/src/console`) and inventory tabs (`ui/src/inventory/{vms,disks,media,networks,vnfs}`) are components, while `ui/src/inventory/app.ts` is the typed tab/readiness shell. The shell and tab islands communicate through `rookery:*` window CustomEvents (`vms-changed`, `add-vm`, `readiness-changed`, `networks-changed`, `interfaces-data`, `interfaces-changed`, `add-network`, `open-tab`, `disks-data`, `disks-changed`, `add-disk`, `media-data`, `media-changed`, `add-media`, `vnfs-data`, `vnfs-changed`, `vpp-ready`, `add-vnf`, `refresh-networks`, `tab-changed`); keep these bridges in sync. Inventory routing is path-based (`ui/src/inventory/router.ts`): tabs are `/vms`, `/disks`, `/media`, `/networks`, `/vnfs`; dialogs use deep links such as `/vms/new`, `/vms/{uuid}/edit`, `/interfaces/{id}/acls`, and `/vnfs/{id}/leases`. `internal/webui.Handler` must keep serving `index.html` for HTML navigations that do not match an embedded asset, or refreshing a deep link returns 404.
- Inventory UI HTTP calls go through `ui/src/shared/api.ts`. It shares in-flight GETs, retries transient failures after 1s/2s/4s/10s, then fails with an `APIError` naming the method and path. Mutations only retry `429`/`503` to avoid duplicate creates. Do not add unbounded retries or unguarded polling loops.
- VM IDs are UUIDs (`internal/store/migrations/0004_vm_uuid.sql`). Use UUID paths/validation consistently; disk and media IDs remain integers.
- `POST /api/vms/{id}/start` and `/stop` drive `internal/qemu`. QEMU runs with KVM (`-accel kvm`), every attached thin-LVM disk as a virtio drive (in `vm_disks.position` order), optional read-only CD-ROM boot media, and `-nic none`. VMs with attached vhost-user interfaces also get `-object memory-backend-memfd,...,share=on` plus `-numa node,memdev=mem`; without shared guest RAM VPP cannot map the virtqueues and the vhost link stays down. VNC is exposed only as a Unix socket under `-run-dir` (default `/run/nerds-vms`). Vhost-user chardevs use `reconnect=1` so QEMU reconnects when VPP recreates its sockets after a restart. QEMU always exposes a `qemu-vdagent` virtio-serial channel (`com.redhat.spice.0`); guests with `spice-vdagent` can exchange clipboard text with the console, while guests without it ignore the port. A QEMU monitor socket (`<uuid>.monitor`) is local-only and used for `SendCtrlAltDel` (`sendkey ctrl-alt-delete`) and `Reset` (`system_reset`).
- `GET /api/vms/{id}/metrics` returns process-level QEMU metrics from `/proc` (summed per-thread `schedstat` CPU, `VmRSS`/`VmSize`, and `/proc/<pid>/io` counters). The endpoint also sums VPP vhost-interface RX/TX counters (via `vppctl show interface <name>`) for the VM's interfaces. The UI **Monitor** dialog polls it every 2s, derives CPU/disk/network rates, and keeps 60 samples for dependency-free canvas history charts; stopped VMs return `running:false`. Do not present these as guest-OS metrics.
- `POST /api/vms/{id}/ctrl-alt-del` and `/reset` inject those commands through the QEMU monitor. The console's Ctrl+Alt+Del button uses the API path first and falls back to VNC key events; Reset falls back to a stop/start power cycle when the monitor socket is missing (for VMs started by older servers).
- `GET /ws/vms/{id}/vnc` proxies the WebSocket to the VM's VNC Unix socket. Keep the `responseRecorder` in `internal/api/server.go` implementing `http.Hijacker` (and `Flush`), or WebSocket upgrades break. The UI console page is `/console.html?vm=<uuid>` and uses the vendored noVNC client. It includes a sticky-modifier virtual keyboard; key definitions use noVNC's `KeyTable` keysyms and standard `KeyboardEvent.code` scancodes. The console **Paste** dialog can type text as US keyboard events (the reliable fallback for guests without clipboard tools) or send it through noVNC `clipboardPasteFrom`, optionally reads the browser clipboard, and falls back to a manual text box when clipboard permissions are unavailable.
- `serve` must start even when prerequisites are missing. It reports state via `GET /api/status`, blocks default-backend disk creation when the bootstrap thin pool is not ready, and blocks `POST /api/vms` until the thin pool, VPP, and at least one unattached disk are ready. Additional storage backends are validated by their driver when a disk is created. Media registration has no readiness gate. Do not turn readiness into a startup failure; QEMU/KVM availability is only checked when a VM start is requested.
- Storage backends are records in `storage_backends` (`0011_storage_backends.sql`): name, title, description, driver, JSON config, and disk count. Only driver `lvm-thin` is implemented now (`config.vg`, `config.thin_pool`, `config.supports_templates`, `config.preparation_script`, `config.preparation_timeout`, `config.allow_template_delete_with_clones`); keep the driver field and API shape extensible for future drivers such as Ceph. `serve` bootstraps a `default` backend from `-vg`/`-thin-pool` when supplied and associates legacy disks with matching `vg`/`thin_pool`; without those flags it uses the first registered backend and updates readiness when a backend is added in the UI. CRUD is at `/api/storage-backends`; changing the driver, volume group, or thin pool is blocked while disks use it, while template/script settings may be updated. Deleting a backend with disks is blocked. LVM backends expose `GET /api/storage-backends/{id}/importable-disks` and `POST /api/storage-backends/{id}/import-disks`; import registers existing thin volumes (via `lvs`) transactionally, marks already-registered volumes, does not mutate LVM, and sizes are rounded up from `lvs --units g`.
- Disks are first-class LVM-backed resources: `POST /api/disks` selects a `storage_backend_id` (or the default backend), runs `lvcreate` for a blank thin volume, or invokes the backend preparation script to clone a template when `template_disk_id` is supplied. Template and clone disks are recorded in migration `0013_disk_templates.sql`; templates are backend-scoped, cannot attach to VMs, and cloning requires `supports_templates` plus a configured script. The script runs as the API user, receives `ROOKERY_DISK_JSON` (operation, request id, disk, template, backend), has a configurable timeout, logs output, and must create the clone LV/device. `PUT /api/disks/{id}` marks/unmarks templates; deleting a template with clones requires `allow_template_delete_with_clones`. `DELETE /api/disks/{id}` still removes empty and clone LVs, with script-based removal for script-created clones. VMs can have multiple disks through the `vm_disks` join table (`0012_vm_disks.sql`); `vms.disk_id` remains the legacy primary/first-disk column and is kept in sync. VM creation requires at least one `disk_ids` entry (`disk_id` is accepted as a single-disk alias); `PUT` with `disk_ids` replaces the set only while stopped, and omitting it preserves the set. A disk can attach to only one VM; deleting a VM releases all of its disks. Keep the host operations and store records consistent (rollback the LV if the DB insert fails; delete the LV before the record).
- Installation media are read-only path-backed records: `POST /api/media` stats an existing absolute regular file, records its server-derived size, and never copies or modifies it. `DELETE /api/media/{id}` removes only the inventory entry and is blocked while a VM uses the media as boot media.
- VMs have an optional `boot_media_id`. It may be set on create and changed or cleared on `PUT`; unlike disks, one media entry can be used by multiple VMs.
- Console access is controlled by `vms.console_enabled`. New VMs default to disabled; migration `0005_console_access.sql` enables existing VMs. The VNC WebSocket returns `403` when disabled and rechecks every second, closing live sessions after an administrator disables access. Keep this enforcement server-side; hiding the UI button alone is not sufficient.
- Rookery Networks are VPP bridge domains (`networks`) and vhost-user interfaces (`virtual_interfaces`). `POST /api/networks` and `POST /api/interfaces` provision VPP objects through `internal/host.VPPNetwork`; attach/detach is DB-only and must be blocked while the target VM is running. VM creation accepts optional `interface_ids`; VM update accepts `interface_ids` plus `replace_interface_ids` (omitted preserves attachments; an empty list with the replace flag detaches all) and must reject interface changes while QEMU is running. VM start turns each attached interface into a QEMU vhost-user netdev; VM deletion detaches its interfaces. VPP state is in memory; on API startup, bridge domains, vhost-user interfaces (by name), NAT44/BVI state, and VNF taps are reconciled. QEMU chardevs use `reconnect=1`, so VMs started with the current arguments can reattach after the vhost socket is recreated; VMs started by older servers without reconnect still need a restart.
- ACLs are named ordered permit/deny rule sets in `acls` (`0010_acls.sql`), with `virtual_interfaces.ingress_acl_id`/`egress_acl_id` kept as the first entry of each direction for compatibility and ordered assignments in `interface_acls` (`0016_interface_acls.sql`). Each rule also has its own optional description (documentation only). Rules support CIDR prefixes, protocols, and TCP/UDP port ranges; VPP enforcement uses the ACL plugin (`acl_add_replace`, `acl_interface_set_acl_list`) and `vpp_index` persistence. ACLs are assigned by name through `PUT /api/interfaces/{id}/acls`, which accepts repeated `ingress_acls`/`egress_acls` in evaluation order (the legacy single `ingress_acl`/`egress_acl` fields still work); the UI labels ingress as **From interface** and egress as **To interface**, with up/down ordering. Assignment requires VPP readiness. Reconcile ACL definitions and interface assignments after vhost reconciliation and on VPP restart. Deleting an assigned ACL is blocked. The UI lives under **Rookery Networks**, includes a rule editor with full ACL preview, and shows assignments on interface rows.
- Route tables are VPP IP FIB/VRF definitions in `route_tables` (`0017_route_tables.sql`); table `0` is the implicit default for both families and is synthesized in `RouteTableService`, not stored. Custom tables have a name, table ID, and IPv4/IPv6 family, with unique `(table_id, is_ipv6)` and `(name, is_ipv6)`. `PUT /api/interfaces/{id}/route-tables` binds `ipv4_table_id`/`ipv6_table_id`; `virtual_interfaces` stores both (default 0) and `interfaceSelect` joins the table names. Static entries live in `routes` (`0018_routes.sql`): table ID/family, prefix, next hop, optional egress interface, and a unique `(table_id, is_ipv6, prefix)`. `GET`/`POST /api/route-tables/{id}/routes?ipv6=<bool>` list/add entries and `DELETE /api/routes/{id}` removes one; routes in the default table use ID `0`. VPP uses `ip_table_add_del`, `sw_interface_set_table`, and `ip_route_add_del`; startup reconciliation ensures custom tables, reapplies interface bindings, then reinstalls routes. `GET /api/route-tables/{id}/fib?ipv6=<bool>` reads the live VPP FIB with `ip_route_v2_dump`, including connected, DHCP, ND, and adjacency entries with source names and paths; the route editor shows these read-only as **Dynamic routes** for troubleshooting. Deleting a custom table is blocked while an interface or route references it. The UI has a **Route tables** subtab, an interface-level binding dialog, and a per-table route editor.
- Network functions are first-class records in `vnfs` (`0008_vnfs.sql`): `dhcpv4`, `dhcpv6`, and `nat44` types, a network, an enable flag, typed JSON config, and tap metadata. A network can have at most one VNF of each type; use separate networks for separate DHCP pools. The UI exposes a **VNFs** tab; `POST /api/vnfs`, `PUT /api/vnfs/{id}`, `DELETE /api/vnfs/{id}`, `POST /api/vnfs/{id}/restart`, `GET /api/vnfs/{id}/leases`, and `GET /api/vnfs/{id}/sessions` manage them.
- `internal/host.VNFManager` runs one in-process CoreDHCP server per enabled DHCP VNF. Each DHCP VNF gets a `vnf<id>` VPP tap, a gateway address, an allocator, and a JSON lease file under `<run-dir>/vnfs/<id>.json`. DHCPv4 uses the bitmap allocator; DHCPv6 is stateful IA_NA (no RA/PD). DHCPv4 also supports `static_assignments` (unique MAC/IPv4 pairs): reserved addresses are excluded from the dynamic pool, may sit inside or outside the DHCP range, and must not be the gateway or service address. Static assignments are DHCPv4-only. Leases are surfaced by VNF ID, and status is `running`, `disabled`, or `degraded`. Enabling/restarting needs VPP, UDP 67/547, `SO_BINDTODEVICE`, and tap configuration, so it needs root or `CAP_NET_ADMIN` + `CAP_NET_BIND_SERVICE` + `CAP_NET_RAW`. Failures must roll back the tap and leave the VNF disabled.
- DHCPv4 uses a memif transport by default (`-dhcp-transport memif` / `NERDS_VMS_DHCP_TRANSPORT=memif`; set `tap` to fall back). VPP is the memif master; the API is the slave using `go.fd.io/govpp/extras/gomemif/memif` (do not vendor or replace it). `internal/host/memif_dhcp.go` runs gvisor netstack over the memif, reuses the CoreDHCP plugin handler, and binds UDP/67 on the VNF's `BindIP` when set, otherwise on the configured gateway (`memif_sw_if_index`/`memif_socket`/`memif_host_name` columns in `0014_vnf_memif.sql`/`0015_vnf_memif_name.sql`). The VPP memif interface name is the VNF name, not `vnf<id>`. On non-NAT networks the memif netstack owns the gateway address directly; there is no separate gateway tap and no host forwarding. NAT networks keep `.1` on the BVI. The memif socket lives under `/run/rookery/memif/<vnf-id>.sock` (configurable with `-memif-dir` / `ROOKERY_MEMIF_DIR`), and DHCPv6 still uses the tap path.
- NAT44 is IPv4-only (`internal/host/nat44.go`, `internal/api/nat44.go`). It creates a per-network BVI (`bvi<id>`) and stores `bvi_host_name`, `bvi_sw_if_index`, and `ipv4_gateway` on `networks` (`0009_nat44.sql`). Enabling it refuses any host default-route NIC and wireless NICs, flushes the selected wired outside NIC, creates a VPP `host-<nic>` using the physical NIC's MAC (random MACs break upstream ARP/switch port security), configures NAT44-ED via the binary API (interface features are not idempotent in the VPP CLI), and uses a static outside address/default route or the VPP DHCP client (which installs its leased address and default route). DNAT/port-forwarding rules live in `VNFConfig.DNATRules` and are applied as VPP NAT44 static mappings through `Nat44AddDelStaticMappingV2`; use the outside interface's `sw_if_index` so the external address follows DHCP changes, and tag mappings `nerds-vms:<vnf-id>:<rule-index>` so applying/removing one VNF never touches another VNF's rules. Apply DNAT mappings after `ApplyNAT44` and remove them before `RemoveNAT44`. Startup reconciliation order is bridge domains, enabled NAT44 VNFs, then DHCP VNFs. A DHCPv4 VNF on a NAT network runs on `.2` while the BVI owns `.1`; `BindIP` is the server ID and must not be compared with `gateway` in DHCP request filtering. Validate/take over the outside interface before creating a BVI, roll back a newly created BVI when activation fails, and remove a leftover BVI when deleting a NAT44 VNF unless another NAT44 or NAT-adjusted DHCPv4 VNF depends on it.
- On API startup, `internal/api.Server.RunInfrastructureReconciler` waits for VPP, ensures every recorded network bridge domain exists with its stored ID (`EnsureBridgeDomain`), finds or recreates every recorded vhost-user interface by name and updates its `sw_if_index`/socket metadata, restores ACL definitions/assignments, restores enabled NAT44 VNFs, then restarts every enabled DHCP VNF, reusing an existing `vnf<id>` tap and recreating a missing/migrated tap. A VPP restart removes vhost-user interfaces, ACL state, NAT44 state, and VNF taps; API startup restores them; QEMU reconnect lets current VMs reattach, while older QEMU processes may need a restart. While running, `RunInfrastructureReconciler` control-pings the VPP API every five seconds and compares the API socket identity; on restart it resets cached NAT/VNF runtime state and repeats the reconcile sequence automatically. Reconciliation runs in a bounded background worker (2 minutes) so API pings/identity checks continue; a further VPP restart queues another rebuild after the in-flight worker finishes (workers must not overlap, because concurrent BVI creation aborts VPP). `vppctl` calls have a 10-second timeout so a disappearing CLI socket cannot wedge the reconciler.
- Migration `0008_vnfs.sql` converts existing network-level DHCP settings into a DHCPv4 VNF. On the first startup reconciliation or manual restart, `internal/api.cleanupLegacyNetworkVNF` removes the old `ndn<network-id>` tap and legacy DHCP files. The old network DHCP API/UI is removed; do not add new code that writes the legacy `networks.dhcp_*` columns.
- `internal/api.Server.resourceMu` serializes disk provisioning with VM attachment; preserve it or replace it with equivalent concurrency control.
- The Network tab includes a **Troubleshoot** section. `GET /api/troubleshoot/vpp-graph` runs `vppctl show vlib graphviz filter`, parses the active nodes and edges, and returns them as JSON; the UI renders a dependency-free layered top-to-bottom SVG with input nodes at the top, terminal/drop nodes at the bottom, barycenter ordering to reduce crossings, and dashed feedback edges. Interface-related nodes are ringed and a **Focus** picker filters the graph to one interface group or packet feature (ACL plugin, NAT44, DHCP) plus its direct neighbors; hover isolates a node and its direct neighbors, and labels/edges for everything else are hidden. It supports wheel/button zoom, drag-to-pan, Fit, and a Labels toggle. VPP's CLI pager can split long DOT node lines across physical lines, so join quoted statements until complete instead of parsing one statement per line. Node size represents cycles/packet and color represents packets/call. Interface nodes only exist in the graph when active since the last stats clear. Packet capture lives in the separate capture endpoints described below; trace is still a follow-up. Keep the `vppctl` timeout and VPP readiness checks when extending this endpoint.
- The VPP socket is the binary API socket (`socksvr`, default `/run/vpp/api.sock`), checked with `go.fd.io/govpp`, not the CLI socket or a vhost-user socket. NAT44 also shells out to `vppctl` (default CLI socket) for plugin/address/session commands, so it must be on `PATH` with CLI socket access. `GET /api/host/interfaces` exposes physical and external host interfaces, link/address state, and whether each has a matching `host-<nic>` interface in VPP; Rookery/VPP-created interfaces (`vnf*`, `tap*`, `host-*`, etc.) are filtered out. Default-route takeover is blocked server-side.
- `GET /api/troubleshoot/acl-counters` exposes per-interface ACL rule-match counters by combining `show acl-plugin lookup context` with `show acl-plugin tables applied`. The `hitcount` values are explicit per-rule matches per lookup context (ingress/egress), split by action into denied/permitted and returned with ACL/rule indexes; implicit-deny packets are not counted. The UI shows compact totals and expandable per-rule counters in the Interfaces tab, where ACLs are assigned. Keep `VPPInterfaces` for the sw_if_index-to-name mapping.
- Packet capture is managed by `internal/host/pcap.go` through `vppctl pcap trace`. VPP writes only a basename under `/tmp`, so capture files are named `rookery-<timestamp>-<random>.pcap` and read from `/tmp`. The API keeps one active capture; `max <packets>` is derived from the requested max size and snapshot length (`ceil(max_bytes/(snap_length+16))`, capped at 1,000,000). Capture listing/download/delete is available even when VPP is down; the active file cannot be deleted until capture stops. Endpoints live under `/api/troubleshoot/capture`; `VPPInterfaces` uses govpp for the picker. Like NAT44, capture requires the VPP CLI socket and root/CLI access.
- WebShark v3.0.0 is vendored under `internal/webui/static/webshark` (GPL-2.0, see its `LICENSE.txt`/`README.txt`); Roboto and Material Icons woff2 files are vendored under `fonts/` so icons work without external font CDNs. `internal/webui.Handler` maps `wiregasm.wasm`/`wiregasm.data` requests to the upstream `.gz` assets; the upstream `ffmpeg-core.wasm` is intentionally omitted, so RTP audio playback is unavailable. The Go API implements the small WebShark storage API (`/webshark/json?method=files|download`, `/webshark/captures/{name}`, `/webshark/watch`). The `/webshark` route needs a relaxed CSP (`unsafe-inline`, `unsafe-eval`, `wasm-unsafe-eval`, blob workers) and `X-Frame-Options: SAMEORIGIN`/`frame-ancestors 'self'` so it can be iframed; keep the stricter CSP for the main app.
- `TapCreateV2` must use `ID: ^uint32(0)` for automatic tap device allocation. Sending the Go zero value requests device instance 0; after the first tap exists, later taps fail with `VppApiError: Invalid interface (-71)`.
- SQLite uses the pure-Go `modernc.org/sqlite` driver, so builds need no CGO. The module targets Go 1.24 and pins `modernc.org/sqlite` v1.45.0, the newest release compatible with that Go version.
- Authentication and authorization are intentionally absent. The server binds to `127.0.0.1:8080` by default; do not expose it without an access-controlled proxy. `serve` applies a per-path token-bucket rate limit to every request on both HTTP listeners (`-rate-limit` / `NERDS_VMS_RATE_LIMIT`, default 3 RPS per URL path, `0` disables); excess requests get `429` with `Retry-After: 1`.
- Verify with `go test ./...`, `go vet ./...`, and `gofmt -l .`; run locally with `go run ./cmd/nerds-vms-api serve -db /tmp/nerds-vms.db`.

## Conventions and gotchas
- Every playbook except `setup-vpp.yml` sets `gather_facts: false`; do not use `ansible_facts` there without enabling fact gathering.
- Defaults live in each playbook's `vars:` block; required values are validated at runtime, so pass e.g. `-e vg_name=vg0 -e disk_lv=...` explicitly.
- `setup-vpp.yml` restarts VPP via handlers and calls `meta: flush_handlers` before waiting on `/run/vpp/cli.sock`; preserve that order when editing.
- README's `create-instance-disk.yml` example uses `base_lv=debian-13-template`, but `setup-template.yml` actually creates `debian-template` by default.
